# podflow

個人利用向けのポッドキャスト再生 PWA。iPhone での利用を前提に作っているが、
ホーム画面への追加の案内など、環境で違う部分は Android でも成り立つようにしてある。ビルド不要の静的サイト（素の HTML / CSS / ES Modules）で、
Cloudflare Pages の無料枠にそのまま置いて iPhone のホーム画面から使うことを想定している。

## 実装済みの要件

| 要件 | 実装 |
|---|---|
| エピソード一覧 | 番組ごとに一覧表示（タイトル / 公開日 / 再生時間 / 既読・未読） |
| **極めて少ない手数での並び替え** | 一覧上部に**常時固定**したトグルを 1 タップで昇順⇄降順が反転（メニューを開く操作なし）。番組ごとに設定を保存 |
| バックグラウンド再生 | `<audio>` + Media Session API。ロック画面から再生 / 一時停止 / 15秒シーク |
| ミニプレイヤー | 全画面共通で下部に固定。上端に指で掴めるシークバーを通し、経過 / 全体の時間と、塗りつぶしの丸い再生ボタンを出す。一覧に埋もれて再生が始まったことに気付けない、という指摘への対処なので、影と面の明るさで一覧から浮かせてある |
| 続きの読み戻し | 起動時に、最後に聴いていた回をミニプレイヤーへ止まった状態で戻す。音源は再生ボタンが押されるまで載せない（開いただけで通信しない） |
| 連続再生 | エピソードが終わると一覧の次の回へ自動で送る（フィルタで隠れている回は飛ばす）。ロック画面のスキップボタンでも前後の回へ移動できる |
| 一括で再生済みにする | 各行の ⋮ から「ここまで再生済みにする」。他のアプリから乗り換えたときに続きから始められるようにするため |
| 全て未再生に戻す | エピソード一覧の右上 ⋮ から「全て未再生に戻す」。同じメニューに「最新のエピソードを取得」もある |
| 再生済みフィルタ | 一覧上部のトグルを1タップで「すべて表示 / 未再生のみ」を切り替え。番組ごとに保存 |
| 番組一覧の表示 | フォロー中一覧の上に**常時固定**したトグルを 1 タップで フォローした順 → 更新が新しい順 → 五十音順 と巡回（既定はフォローした順）。各行に、表示順 / フィードで一番新しい回の公開日 / 再生済みと全件を出す。新着を強調する印は付けず、どの番組も同じ見た目にする。更新日と全件は番組を開いたときに `follows` へ控えた値、再生済み件数は `episodes` の索引から数えるので、ホームの描画でフィードは取りに行かない |
| 新着の自動取り込み | 番組を開くとキャッシュから即座に表示し、裏で新着だけを取りに行く。端末が受け取るのは増えた回のぶんだけ。全体を取り直すのは ⋮ →「最新のエピソードを取得」のときだけ |
| 引っ張って更新 | エピソード一覧とホームの両方で、上端から下に引くと新着を確かめ直す。エピソード一覧は開いたときと同じ差分の確認、ホームはフォロー中の全番組をまとめて確認（3本ずつ流す）。ホームは普段いっさい通信しないので、まとめて確かめられるのはこの操作だけ。見つかっても知らせは出さず、一覧と更新日が変わるだけ。手応えは iOS の標準に合わせ、一覧そのものが指に付いて下がり、引くほど重くなる（`pullResistance`） |
| フィード取得の冗長化 | 直接取得と公開プロキシ3種を同時に投げ、最初に成功したものを採用。全滅時は経路ごとの理由と再試行ボタンを表示 |
| iPhone (Safari/PWA) | standalone 表示、セーフエリア対応、初回再生は必ずタップイベント内で `play()` |

意図的に実装していないもの: プッシュ通知 / ダウンロード・オフライン再生（ストリーミングのみ）/
おすすめ・ランキングの提示（番組は名前で検索して追加する）/ 最新回の抜き出しや未再生件数のバッジ。
薦めない・急かさないことをアプリの説明文にも書いてあるので、増やすときはそこと矛盾しないか見ること。

## 画面

```
/                     ホーム（フォロー中の番組）
/search               番組検索
/show?feed=<フィードURL>  エピソード一覧
/player               フルプレイヤー（他の画面に重ねて表示）
/help                 使い方（他の画面に重ねて表示）
```

画面遷移は History API で行い、`#` は使わない。実体の無いパスは `_redirects` の
`/* /index.html 200` で `index.html` に落とすため、どの画面で再読み込みしても開ける。
Functions は `_routes.json` で `/api/*` だけに限定してあり、この書き換えの影響を受けない。
ミニプレイヤーは全画面共通で下部に固定し、題名の側をタップするとフルプレイヤーへ。
シークと再生 / 一時停止はミニプレイヤーだけで済むので、フルプレイヤーは 15 秒スキップと
再生速度のための画面になっている。

使い方（`index.html` の `#help`）は機能を変えたら追従させること。

## 現在の稼働構成

- ホスティング: Cloudflare Pages（無料枠）。URL にアカウント名が入らない
- フィード取得: `functions/api/feed.js`（Pages Functions）。アプリと同じオリジンで動くため
  CORS の問題が起きず、公開プロキシのようなサイズ上限もない。アプリからは `./api/feed?url=`
  という相対パスで呼ぶので、コードのどこにもホスト名が入らない
- iPhone 実機で確認済み: フィード取得 / 並び替え / 再生 / 既読・再生位置の保存 /
  連続再生 / バックグラウンド再生 / ロック画面操作 / ホーム画面に追加しての standalone 起動

## iOS アプリとして包む（native/）

**画面を消したまま一時停止したあとイヤホンから再開する**、この一点だけは Web では解けない
（上記「iOS 上の注意点」を参照）。解くには音声再生をネイティブに持つ必要があるため、
`native/` に Capacitor の入れ物を置いている。

- **Web の配信物はリポジトリ直下が正**。`native/` はそれを写して包むだけで、二重管理はしない
  （`native/scripts/copy-web.mjs` が `index.html` / `css` / `js` / `icons` を `native/www` へ写す）
- ネイティブでは Service Worker を登録しない（`window.__PODFLOW_NATIVE__`）。中身は `.ipa` に
  同梱されていて更新は入れ直しで行うため、キャッシュ層を挟む意味が無い
- `Info.plist` の `UIBackgroundModes: audio` が背面再生の前提。外すと画面を消した時点で止まる

### ビルド（Mac は要らない）

`.github/workflows/ios.yml` が GitHub Actions の macOS ランナーで `.ipa` を組み立て、
成果物として置く。**署名はしない**（無料の Apple ID で署名するのは SideStore 側の役目）。

### 端末へ入れる

SideStore で入れる。初回だけ Windows PC が要り、以降は端末内で更新される。
無料の Apple ID は同時3アプリ・証明書は7日で失効するが、SideStore が自動で更新する。

## デプロイ（Cloudflare Pages）

ビルド不要。リポジトリ直下がそのまま公開ディレクトリで、`functions/` は自動で認識される。

1. https://dash.cloudflare.com/ → Workers & Pages → Create → **Pages** → Connect to Git
2. リポジトリを選ぶ（非公開リポジトリでも無料枠でビルドできる）
3. ビルド設定
   - Framework preset: **None**
   - Build command: **空欄**
   - Build output directory: **`/`**
4. Save and Deploy → `https://<プロジェクト名>.pages.dev` が公開 URL
5. iPhone の Safari で開き、共有 → **ホーム画面に追加**（PWA として standalone 起動する）

push するたびに自動で再デプロイされる。

Service Worker と Media Session は HTTPS でのみ動く。ローカル確認は `localhost` なら可。
ただし `./api/feed` は Pages Functions なので、素の静的サーバーでは動かない
（`npx wrangler pages dev .` を使うか、公開プロキシへのフォールバックで確認する）。

```bash
npm start   # http://localhost:8080 で配信（中継は動かない）
```

## 設定の差し替え

外部サービスに依存する値は `js/config.js` の 1 箇所に集約してある。

- `FEED_SOURCES` — RSS の取得経路。全経路を同時に投げ、最初に成功したものを採用する。
  同一オリジンの中継 → 直接取得 → 公開 CORS プロキシ 3 種。公開プロキシは中継が使えない
  ときの保険で、エピソード数の多い番組（RSS が数 MB）ではサイズ上限に当たって失敗する
- `FEED_FETCH_TIMEOUT_MS` — 1 経路あたりの上限時間（既定 40 秒）。同時に投げるのでこれが最大待ち時間になる
- `FEED_CACHE_TTL_SEC` — フィードキャッシュの有効期限（既定 900 秒 = 15 分）。
  番組を開いたときは期限に関わらず更新の有無を確かめるので、これは中継が使えない
  環境で全体を取り直す間隔として効く
- `APP_VERSION` — ホーム画面下部に出る版。配信するたびに更新する

iTunes Search API は CORS 許可済みのためプロキシを通さず直接 fetch している。

### 新着の確認（条件付き取得と差分）

エピソード数の多い番組は RSS が数 MB あるため、開くたびに全体を落とすのは現実的でない。
端末が受け取る量を次の 2 段で抑えている。

1. **変わっていなければ 0 バイト** — 中継に `etag` / `modified` を渡すと、配信元へ
   `If-None-Match` / `If-Modified-Since` を付けて問い合わせ、変わっていなければ本文なしで返す
   （ブラウザのキャッシュ機構と紛れないよう 304 ではなく 204 を使う）
2. **変わっていれば増えた分だけ** — 手持ちで一番新しい回の `<guid>`（無ければ音声URL）を
   `after` として渡すと、中継がそれより新しい `<item>` だけを抜き出して返す。
   RSS に部分取得の仕組みは無いので、配信元と中継の間は全体のままだが、端末が受け取るのは
   増えた回のぶんだけになる。応答には `x-feed-partial: 1` が付き、端末は置き換えではなく
   手持ちへの追加として扱う

目印が見つからない場合（フィードが作り直された、など）は差分にせず全体を返す。
印を返さない配信元では、取得した中身を突き合わせて変化の有無を判定する。
⋮ →「最新のエピソードを取得」は、この経路を通さず全体を取り直す。

## データ構造（IndexedDB: `podcast_pwa_db`）

| ストア | keyPath | 用途 |
|---|---|---|
| `follows` | `feedUrl` | フォロー中の番組。`title` / `artworkUrl` / `sortOrder` / `hideRead` / `followedAt` / `latestPubDate` / `episodeCount` |
| `episodes` | `episodeId` | 既読・再生位置。`feedUrl` に**インデックス**を張り番組単位で取得。`lastPlayedAt` が一番新しい未読の回が、起動時に読み戻す「続き」になる |
| `feedCache` | `feedUrl` | RSS パース結果と `cachedAt` / `ttl`、更新確認用の `etag` / `lastModified` |

`episodeId` は `<guid>` があれば `${feedUrl}::${guid}`、無ければ `${feedUrl}::${hash(audioUrl)}`（FNV-1a）。

## 実機での切り分け

開発者コンソールが使えない端末で原因を追うための仕掛けを入れてある。

- ホーム画面の一番下に**版**（`js/config.js` の `APP_VERSION`）を表示する。
  端末に新しいコードが届いているかはここで判断する
- その版をタップすると、再生まわりのイベント記録（`play` / `pause` / `ended` /
  `advance` / `play-rejected` / `restore` / `re-arm` / `resume-rejected` など、
  時刻と再生位置つき）を表示する。`restore` は起動時に続きを読み戻したこと、
  `re-arm` は音源を載せ直して再生し直したことを表す
- Service Worker は同一オリジンの取得を `cache: 'no-cache'` で行う。
  ホスティングが付ける `max-age` により、素直に取得すると十数分ぶん古いコードが
  返って原因の切り分けができなくなるため

## アイコン

`icons/source.png` から各サイズを生成している。いずれも 256 色に減色した PNG。

| ファイル | 用途 | 加工 |
|---|---|---|
| `icon-192.png` / `icon-512.png` | 一般 | そのまま縮小 |
| `icon-512-maskable.png` | Android | 丸や角丸に切り抜かれても欠けないよう中央 90% に配置。元画像の角の黒が残らないよう、同じ角丸で切り抜いてから背景に載せている。背景は元画像の縁の色をそのまま横へ伸ばした縦グラデーションなので、周りとの継ぎ目が出ない |
| `apple-touch-icon.png` | iOS のホーム画面・タブ | iOS のマスクと元画像の角丸が二重にならないよう、わずかに拡大して角を落とす。iOS が確実に読むのは PNG なのでこの形式に固定 |

減色しないと 512 が 200KB 近くになる。WebP のほうがさらに小さくなるが、この絵柄では
減色 PNG のほうが元画像に忠実（RMSE 1.30 対 2.03）で、形式も 1 つで済むため PNG に揃えている。

## テスト

iTunes Search API と RSS をモックし、音声だけは Range 対応のローカルサーバーから実際に再生させて、
検索 → フォロー → 並び替え → 再生 → 進捗保存 → 既読化までを通しで検証する。

```bash
npm install   # playwright
npx playwright install chromium
npm test      # 中継の差分抽出（test/function.mjs）→ 画面の通し検証（test/smoke.mjs）
```

一括操作はどちらも、実行前に対象件数を確認し、実行後に「取り消す」ボタン付きの通知を出す。
取り消しは変更前の状態（既読かどうかと再生位置）をそのまま書き戻すので、元通りになる。

## 設計時の未確定事項について決めたこと

- **フォロー後の遷移先**: そのままエピソード一覧へ移動する（`js/app.js` の `data-follow` ハンドラ）
- **番組一覧の並び順**: 3つ持ち、ホームのトグルで選ぶ（`js/db.js` の `FOLLOW_ORDERS`）。
  1タップで次へ送るのはエピソード一覧の並び替えと同じ操作感にするため

  | 並び順 | 内容 |
  |---|---|
  | `followed`（既定） | フォローした順。新しく追加したものが上。番組を追加したとき以外は入れ替わらない |
  | `updated` | フィードの更新が新しい順。一度も開いていない番組は更新日を持たないので末尾 |
  | `title` | 題名の五十音順（`Intl.Collator('ja')`）。漢字で始まる題名は読みが無いため字の並び順になる |

  既定を `followed` にしてあるのは、**選んでいないのに**新着のある番組が上へ来ないようにするため。
  強調しないことと、知る手段を持たないことは別なので、`updated` は選べば使える。
  どの順でも最後は `followedAt` → 題名 → `feedUrl` で決着させ、描き直しても同じ場所に落ち着かせる
  （`followedAt` を持たない、この項目より前に追加した記録があるため）。
  選択は端末ごとの設定が1つあるだけなので `localStorage`（`podflow.followOrder`）に置く。
  同期的に書けるため、描き直しの途中で画面を閉じられても設定が失われない
- **連続再生の順番**: 一覧の表示順（並び替えとフィルタを適用した後の順番）に従う。
  再生開始時にその順番をキューとして `player` に渡し、各要素に再開位置を持たせている。
  `ended` ハンドラ内では DB の読み取りを待てない（待つと iOS で自動再生が途切れる）ため
- **feedCache の TTL**: 900 秒（`js/config.js`）

## iOS 上の注意点

- 音声はユーザー操作を起点にしないと再生できないため、`player.play()` はタップハンドラ内から
  同期的に呼ぶこと（`await` を挟むと再生がブロックされる）。再生位置の復元も、描画時に読み込み済みの
  状態から同期的に渡している
- Media Session の `artwork` は表示不具合の報告があるため最初から設定していない
- 曲の切り替え時に `audio.load()` を呼んではいけない。ユーザー操作で得た再生許可が外れて
  自動送りの `play()` が拒否されることがある。`src` の代入だけで読み込みは始まる
- `ended` は必ずしも発火しない。末尾までシークした場合などは `pause` で終わることがあるため、
  連続再生は `ended` だけに頼らず「終端に達した状態での停止」からも次へ送る
  （二重に送らないよう、送り済みの episodeId を覚えておく）
- それでも自動再生が拒否された場合は理由をトーストで出す（黙って止まらないようにするため）。
  メタデータは次の回のままなので、ロック画面の再生ボタンでそのまま続けられる
- **ロック画面／イヤホンからの再生では、`<audio>` をそのまま鳴らすだけにする**
  （`setupMediaSession()` の `play` ハンドラ。`resume()` を通してはいけない）。
  `resume()` は状況次第で音源を載せ直す（`src` の代入）が、画面を消している間にそれをやると
  WebKit が再生セッションを作り直し、「今再生中」の役目をその場で手放してしまう。
  イヤホンの再生ボタンが直前に鳴らしていた別のアプリ（ミュージックなど）へ渡り、
  こちらは鳴らないまま、向こうの音楽が鳴り出す。
  込み入った復旧は、前面でしか押せないアプリ内の再生ボタン（`resume()`）に任せる
- **アプリ内の再生ボタンが効かない条件**（`player.resume()` で全部拾う）。
  押しても何も起きない状態が3つあり、いずれも `audio.play()` を呼ぶだけでは音が出ない。
  1. アプリが読み直された・iOS が背面の PWA を終了させた — `<audio>` も Media Session も
     消えている。起動時に `restoreLast()` で最後に聴いていた回を読み戻し、
     再生ボタンが押された時点で `src` を載せてから鳴らす
  2. iOS が読み込み済みの音声を捨てた — `src` はあるが鳴らせない。`error` も付かないまま
     拒否されることがあるので、拒否されたら一度だけ載せ直して鳴らし直す
     （別の回を選び直したことによる `AbortError` は対象外）
  3. 聴き終えた回で止まっている — 終端から `play()` しても進まない。
     キューに次があれば次へ送り、無ければ頭から鳴らす
- **画面を消したまま一時停止すると、イヤホンからは再開できない**（iOS の制約。Webでは直せない）。
  一時停止でオーディオセッションが落ち、背面からは起き直せない。実機の記録では、データを
  82秒先まで持ち（`r4`）通信も生きている（`n2`）状態で `play` も `playing` も発火するのに、
  再生位置が1ミリも進まなかった。取得ではなく音声の出口が動いていない。
  ネイティブは `AVAudioSession.setActive(true)` で有効化できるが、Web に相当する API は無い
  （`navigator.audioSession` にあるのは種別の `type` だけで、`state` は読み取り専用）。
  ここを解くなら音声再生をネイティブに持つ必要がある。**推測で小手先の対処を積まないこと**
- **セッションを保とうとして駄目だった手**（同じ手を繰り返さないこと）。
  - 別の `<audio>` に無音を鳴らして保つ → **効かない**。止めた後に「新しく再生を始める」ことが
    背面ではできないため、無音自体が鳴り始めない（記録に `hold-start` が出ない）
  - 同じ要素を `muted` にして鳴らし続ける → **効かないどころか悪化する**。
    [WebKit は消音メディアをオーディオセッション不要として扱う](https://webkit.org/blog/6784/new-video-policies-for-ios/)
    （消音動画が自動再生できるのはこのため）。`muted = true` にした瞬間にセッションが解放され、
    イヤホンの操作が直前に鳴らしていた別のアプリ（ミュージックなど）へ渡る
  - 音量を絞って鳴らし続ける → **不可能**。iOS は `audio.volume` を無視する
  - つまり「聞こえないまま鳴らし続ける」手段が存在しない。セッションを保つには実際に音を
    出し続けるしかなく、それは選べない。**Web でできることは尽きている**
- 音源を載せる前（読み戻しただけの状態）は `audio.currentTime` が 0 なので、
  その間は再生位置を書き戻さない。`pagehide` で 0 を書いて保存済みの位置を潰さないため
- 再生中は Service Worker の `controllerchange` で読み直さない。読み直すとその場で音が止まり、
  ロック画面の操作先も消えるため。新しいコードは次回の起動で当たる
- 拡大は3つ重ねて止めている。単独ではどれも取りこぼすため。
  1. `touch-action: pan-y`（縦スクロールだけ許可し、ダブルタップとピンチを塞ぐ）
  2. viewport の `maximum-scale=1, user-scalable=no`（Safari は無視するが standalone 起動では効く）
  3. iOS 独自の `gesturestart` などを `preventDefault` する
  横方向にドラッグするシークバーだけは `touch-action: none` にして自前で操作を受け取る
- iOS 17.4 以降、EU 域内では PWA の standalone 起動が廃止されている（日本は対象外）
- Service Worker / IndexedDB のストレージは Chrome より制限が厳しく、長期間未使用だと破棄されうる
- 画面は中身を組み立て終えてから出す（`showScreen` は最後に呼ぶ）。先に出してから
  埋めると、題名・ボタン・一覧が順に現れる過程がそのまま見える
- 並び順やフィルタの保存は、描き直しより先に始める。描き直しに時間を取られている間に
  画面を閉じられると、書き込みが中断されて設定が失われるため
- エピソード一覧は数百件になるため、組み立ての過程が見えないよう次の3つを守る。
  手持ちがあるときは読み込み表示を挟まず一度で描き切る／行ごとに SVG を置かず
  CSS で描く／`content-visibility: auto` で画面外の行の組版と描画を省く
- 番組画像だけは Service Worker で溜めておく（URL ごとに内容が変わらないため）。
  加えて、フォロー中一覧は内容が同じなら描き直さない。毎回 DOM を作り直すと
  画像の要素も作り直され、読み込みし直しでちらつく
- Service Worker はネットワーク優先にしてある。加えて `index.html` の先頭で現行以外の
  キャッシュを削除してからアプリを読み込むため、古い Service Worker が残っていても
  次回の読み込みで最新のコードに入れ替わる（キャッシュ優先の旧版で更新が届かなくなった経験による）
